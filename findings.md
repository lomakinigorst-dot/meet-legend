## Права ведущего — где именно теряется (03.09, отладочные логи)

Модуль выдачи прав по пропуску (`token_affiliation` в prosody) работает **правильно**:
```
22:55:44  set affiliation=owner  for <ведущий>    ← в пропуске есть moderator
22:56:27  set affiliation=member for <участник>   ← в пропуске прав нет
```
При этом в браузере у участника `getRole()` = `moderator`, `isModerator()` = `true`.

Значит роль поднимает сам MUC prosody уже после назначения принадлежности. Комната создаётся
**немодерируемой** (`muc_room_default_moderated` не задан — проверено, ноль вхождений), и в
такой комнате prosody выдаёт роль модератора всем, у кого принадлежность не «никто».

**Настоящая причина (найдена отладочными логами 03.09, 23:0x):** права даёт **порядок входа**.
В логах видно `Adding policy true for permission muc:automatic-ownership` — prosody делает
владельцем комнаты того, кто вошёл первым. Если ведущий подключился позже или на минуту
отвалился и комната пересоздалась, права ведущего достаются случайному человеку.
Проверено: участник без прав в пропуске, зашедший первым, получает `isModerator() = true`.

Штатная настройка для этого есть в шаблоне образа — `WAIT_FOR_HOST_DISABLE_AUTO_OWNERS`, но
работает только вместе с модулем `wait_for_host`, который у нас не включён. Свой модуль на
хуках входа и создания комнаты автовладение не перекрыл — значит оно выдаётся позже.

Модули MUC, включённые у нас: `muc_hide_all`, `muc_meeting_id`, `token_affiliation`,
`token_verification`, `muc_domain_mapper`, `muc_password_whitelist`, `muc_resource_validate`.
Автоназначения владельца среди них нет; в jicofo `enable-auto-owner = false` — тоже проверено.

⚠️ **Ловушка при починке.** Простой путь — сделать комнаты модерируемыми — опасен: в такой
комнате участник без принадлежности («никто») становится **зрителем и не может говорить**. А у
нас гости заходят анонимно, без пропуска, — они как раз получат «никто». Значит понижать роль
надо точечно, не трогая право говорить.

## Каналы связи

- Постоянный канал (WebSocket) режут корпоративные прокси. Свой резервный путь у Jitsi
  отсутствует — запрос отклонён разработчиками (jitsi-meet#8049), а переопределить канал через
  адрес нельзя: в нашей сборке механизма нет (`hashParams` в бандле — ноль вхождений).
  Решение 03.09: все переведены на обмен обычными HTTP-запросами.
- Канал управления моста (colibri websocket) в образе `stable-11031` **нерабочий**: отвечает
  ошибкой 500 на любой запрос. Проверено обращением напрямую к мосту, минуя оба nginx.

## Мосты

- `octo.enabled = false`. При нескольких мостах без Octo участники одной встречи могут попасть
  на разные мосты и не видеть друг друга. Второй мост 03.09 поднят и сразу остановлен.
- Ключи качества сверены с эталоном внутри образа: `onstage-preferred-height-px`,
  `default-max-height-px`, `use-vla-target-bitrate`, `max-oversend-bitrate` — все существуют.

## Грабли работы (переиспользовать, не переоткрывать)

- Кавычки теряются при передаче скрипта через heredoc и ssh — готовить файл локально,
  проверять синтаксис, заливать `scp`.
- `docker compose up -d <сервис>` тянет за собой зависимости и спотыкается о контейнеры,
  переименованные blue-green деплоем. Нужен `--no-deps`.
- Логи nginx обрезать нельзя без нужды: вместе с ними уходит история разбора созвонов.
- Проверять надо ОБА бандла Jitsi: часть ключей живёт в `lib-jitsi-meet.min.js`, а не в
  `app.bundle.min.js`.


## Грабля: переменная списка модулей затирает штатные

`XMPP_MUC_MODULES` задаёт список модулей MUC **целиком**, а не дополняет его. Записав туда
только свой модуль, я снёс штатный `token_affiliation` — выдача прав по пропуску отключилась
совсем. Правильное значение: `token_affiliation,lg_role_guard`.


## Почему запись не шла из виджета сделки (08.09)

**Метод `profile` НЕ ВОЗВРАЩАЕТ почту вообще** — по документации Битрикса он отдаёт только
`ID, ADMIN, NAME, LAST_NAME, PERSONAL_GENDER, TIME_ZONE`. Почта у сотрудников есть, просто в
этот ответ не попадает. Код читал несуществующее поле:
`email: (d.result.EMAIL || 'b24user-<ID>@1leg.ru')` — и ВСЕГДА брал технический адрес.
Под ним и создавалась встреча — в базе ВСЕ встречи из сделок были такими:

| Технический адрес | Кто это на самом деле |
|---|---|
| `b24user-8425@1leg.ru` | Варенников Матвей (`matveycity24@mail.ru`) |
| `b24user-7147@1leg.ru` | Люшинская Анастасия (`nastya.lush@mail.ru`) |
| `b24user-7149@1leg.ru` | Федулов Артём (`fedylow@mail.ru`) |
| `b24user-1@1leg.ru` | Игорь Ломакин |

Тот же человек, войдя в свою встречу из кабинета под своей почтой, ведущим не признавался —
сравнение идёт по адресу. Без прав ведущего страница встречи не получает ни привязки к встрече,
ни возможности записывать.

Связка «сотрудник ↔ номер в Битриксе» уже ведётся в правах доступа (`users.b24_id`) и у всех
заполнена верно — по ней теперь и узнаём человека.


**Та же ошибка была во втором месте** — `lib/b24-auth.ts` (общая проверка для «КП и аудитов»).
Закрыта тем же способом. Если появится третье место, где опознают пользователя Битрикса, —
брать почту только по `users.b24_id`, из `profile` её взять неоткуда.

## 09.09 — Машинный перевод в зале встречи (Phase 9)

**Что увидел владелец:** контекстное меню на плитке участника — «Отпинить», «Скрыть собственное
представление», «Отразить». Реакция: «что за хрень?», «скрыть собственное представление — тоже ебала».

**Источник:** это НЕ наш текст. Русский словарь идёт внутри образа Jitsi —
`/usr/share/jitsi-meet/lang/main-ru.json` (1536 строк), перевод машинный.
Кальки, найденные сразу: `flip` → «Отразить», `hideSelfView` → «Скрыть собственное представление»,
`showSelfView` → «Показать своё представление», `unpinFromStage` → «Отпинить»,
`bestPerformance` → «Лучшее представление» (на деле — про качество, а не про «представление»).

**Как отдаётся:** обычный файл `https://meet.1leg.ru/lang/main-ru.json`, без версии в имени,
кэш по etag/last-modified. Значит подмена файла подхватывается сразу, без пересборки бандла.

**Механизм правки (чтобы пережило обновление образа):**
свои формулировки лежат отдельным файлом-патчем `branding/lang-ru-overrides.json`;
скрипт `system/connect-lang-overrides.sh` берёт словарь ИЗ ОБРАЗА и накладывает патч сверху.
Наслоения не будет, а новые надписи из свежей версии Jitsi не потеряются.
Скрипт ругается, если строка исчезла из словаря Jitsi, — сигнал проверить после обновления.
Файл монтируется в контейнер (`config/web/lang/main-ru.json`), поэтому переживает пересоздание.

**Ограничение:** после обновления образа jitsi/web скрипт надо прогнать заново — иначе
в зале вернётся машинный перевод. Вписано в процедуру обновления.
