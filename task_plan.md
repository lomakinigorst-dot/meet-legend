## Phase 1 — Права ведущего: закрыть источник
Status: причина найдена, заслонка стоит, полное решение — следующим заходом
Проблема (№22 реестра): участник без прав в пропуске получает в зале роль модератора — отсюда
кнопка «Завершить встречу для всех» у обычного человека.
Установлено отладочными логами: модуль выдачи прав отработал ВЕРНО — ведущему `owner`,
участнику `member`. Значит роль поднимает сам MUC prosody: `member` там получает `moderator`,
хотя должен получать `participant`.
- [x] Отладочные логи prosody — включены, причина поймана, уровень возвращён на обычный
- [x] **Причина установлена точно:** права даёт не пропуск, а ПОРЯДОК ВХОДА. prosody выдаёт
      владение комнатой тому, кто вошёл первым (разрешение `muc:automatic-ownership` — видно
      в отладочных логах). Ведущий подключился позже — и права ведущего достались другому.
      Модуль выдачи прав по пропуску тут ни при чём: он отрабатывает верно
      (`set affiliation=member` для участника без прав — видно в логах).
- [x] Написан свой модуль `mod_lg_role_guard.lua` (лежит в
      `config/prosody/prosody-plugins-custom/`, подключён через `XMPP_MUC_MODULES`)
- [ ] ⚠️ **Модуль пока не перекрывает автовладение.** Пробовал два хука: на вход участника и на
      создание комнаты — роль всё равно остаётся модератором. Значит владение выдаётся ещё
      позже либо иначе.
- [ ] **Следующий шаг:** включить штатный модуль Jitsi `wait_for_host` — в шаблоне образа под
      него есть готовая настройка `WAIT_FOR_HOST_DISABLE_AUTO_OWNERS`, которая ровно это и
      отключает. Проверить, что при этом гости не оказываются заперты до входа ведущего.

⚠️ **Пока держится заслонкой** (`137c2f22`): кнопка «Завершить встречу для всех» скрыта у всех,
кроме ведущего по нашей базе — проверено с обеих сторон. Но человек с лишними правами
по-прежнему может выключить всем звук или убрать участника.

⚠️ **Грабля этого захода:** переменная `XMPP_MUC_MODULES` задаёт список целиком. Записав туда

## Phase 7 — Запись не запускается при входе из приложения Б24 (задача владельца 08.09)
Status: complete — причина устранена, приёмка через браузер пройдена
Симптом: через кабинет запись работает, через виджет в сделке — нет.
**Причина — дефект в коде, подтверждена документацией Битрикса.** Метод `profile`, которым мы
опознаём вошедшего, поля EMAIL не возвращает вообще: только ID, ADMIN, NAME, LAST_NAME,
PERSONAL_GENDER, TIME_ZONE. Почта у сотрудников в Битриксе ЕСТЬ — просто в этот ответ она не
попадает. Код читал несуществующее поле и ВСЕГДА сваливался на технический адрес
`b24user-<ID>@1leg.ru`. Под ним человек в кабинете не значится → не признавался ведущим своей
же встречи → страница зала не получала ни привязки к встрече, ни права записывать.
Первоначальный мой диагноз («почта не заполнена в профиле») был неверен — поправлено.
- [x] Источник найден: в профиле Битрикса не заполнена почта → подставлялся технический адрес
      (`email: (d.result.EMAIL || 'b24user-<ID>@1leg.ru')`)
- [x] Сотрудника узнаём по номеру в Битриксе — связка уже ведётся в правах доступа, у всех,
      кто заводил встречи из сделок, номера совпадают (проверено в базе)
- [x] Найдена и закрыта ТАКАЯ ЖЕ дыра во втором месте — общая проверка для «КП и аудитов»
      (`lib/b24-auth.ts`): тот же код, тот же технический адрес
- [x] Владельцы 8 ранее созданных встреч переписаны на настоящие почты (по «да» владельца).
      Технических адресов в базе не осталось — проверено запросом.
- [x] Проверено фактом: Матвей признан ведущим своей встречи (`isHost: true`, привязка к
      встрече 133) — раньше привязки не было, отсюда и не было записи
- [x] Приёмка через браузер в одноразовой комнате: вход → плашка «Эта встреча должна
      записываться» → «Начать запись» → запись пошла, таймер 0:22, ошибок нет
