# КЛЕО / Hermes (vm-10107, 31.76.102.165) — почему агент замолчал

Разбор построен по истории репозитория `lomakinigorst-dot/kleo-wiki`: сервер сам
пушит туда снимок своего живого конфига и скриптов каждые 5 минут
(`kleo-vault-sync.timer`). Это даёт точную хронологию без доступа к машине.

## Короткий ответ

20 августа маршрут модели переключили с DeepSeek на подписочный Claude Code —
и в тот же коммит попала правка прокси, которая на части запросов отдаёт
**HTTP 200 с пустым телом**. Это и есть «перестал отвечать»: не ошибка, а тишина.
Коммит с этим переключением — **последний в репозитории**. После него сервер не
записал ни одной строки памяти.

## Хронология

| Когда (MSK) | Что | `model.default` / `provider` |
|---|---|---|
| 01–11 авг | штатная работа, эксперименты с маршрутами | `deepseek-v4-flash` / `deepseek` |
| 11 авг 04:21 | последний заведомо рабочий снимок | `deepseek-v4-flash` / `deepseek` |
| **20 авг 20:28** | **переключение на подписку Claude Code** | `claude-code:claude-code-opus` / `claude-code` |
| 20 авг 20:28 → сейчас | **синхронизаций больше нет** | — |

Коммит `f4fe5cb` «KLEO memory sync: 2026-08-20T17:28:49Z» изменил ровно два файла:

1. `config.yaml` — `default: deepseek-v4-flash` → `claude-code:claude-code-opus`,
   `provider: deepseek` → `claude-code`, а также `providers.claude-code.default_model`
   `claude-code-sonnet` → `claude-code-opus`.
2. `claude-code-openai-proxy.py` — правка «уважать запрошенную модель».

Таймер синхронизации работает независимо от модели и коммитит при любом изменении
vault. Полное молчание с 20 августа означает, что агент перестал писать память
именно в момент переключения.

## Причина №1 — доказанный дефект: HTTP 200 с пустым телом

В правке от 20.08 переменная `_resp_model` объявлена внутри метода `do_POST`
(строка 229), а используется внутри **другого** метода — `send_sse_completion`
(строки 143, 150, 157). В Python это разные области видимости, и глобальной
переменной с таким именем нет.

Воспроизведено локально на подставном `claude`:

```
--- ORIGINAL : stream=true ---
HTTP 200, тело 0 байт
NameError: name '_resp_model' is not defined
  File "claude-code-openai-proxy.py", line 143, in send_sse_completion
    "model": _resp_model,
```

Ключевая деталь: заголовки `200 OK` отправляются **до** падения, поэтому клиент
получает не ошибку, а корректный ответ нулевой длины. Ни в Telegram, ни в логах
Hermes это не выглядит как сбой — просто пустота. Ровно тот симптом, который вы
описали.

Срабатывает на запросах с `"stream": true`. В снимке конфига стриминг у провайдера
`claude-code` выключен (`streaming: false`), поэтому обычный чат мог идти мимо
дефекта — но любой подсистемный вызов со стримингом (делегирование, сжатие треда,
хуки памяти) попадал в него гарантированно. Что именно случилось на живом сервере,
однозначно покажет журнал:

```bash
journalctl -u claude-code-proxy --since '10 days ago' | grep -i -E 'nameerror|_resp_model'
```

Это первое, что собирает `kleo-diagnose.sh`.

## Причина №2 — маршрут по умолчанию стал тяжёлым

После 20.08 **каждое** сообщение в Telegram идёт не в HTTP API, а поднимает
отдельный процесс `claude -p` — и в самой тяжёлой конфигурации:

- `--model opus` вместо `sonnet` (изменено тем же коммитом);
- `--add-dir /opt/kleo/obsidian-vault --allowedTools Read Grep Glob --max-turns 12` —
  то есть полноценная агентная сессия с обходом vault, а не мост к модели;
- промт до 160 000 символов;
- таймаут 360 секунд;
- `ThreadingHTTPServer` без ограничения параллелизма.

Каждый такой процесс — Node на сотни МБ. Пять активных топиков → пять-семь
процессов разом. Этот сценарий у вас уже был, он записан в vault от 06.08:

> «Модель внутри прокси начинает выполнять инструкции вместо ответа, выжигает
> лимит ходов и падает — **все топики зависают**.»

Тогда это лечили переводом дефолта обратно на DeepSeek. 20 августа конфигурацию
вернули в то же состояние, но уже с opus вместо sonnet.

Отдельно: комментарий в коде прямо говорит, что прокси должен быть «мост к модели,
а не второй агент», но флаги `--add-dir` / `--allowedTools` / `--max-turns 12` из
команды так и не убрали — они на месте с 05.08. Заявленная починка не была доведена.

## Причина №3 — недельный лимит подписки (вторичная)

Opus на подписке Claude Code расходует недельный лимит в разы быстрее sonnet.
При исчерпании прокси возвращает 429 с текстом про лимит — то есть сообщение в
Telegram всё-таки приходит. Само по себе это не даёт молчания, но ускоряет выход
из строя основного маршрута. Проверяется тем же журналом (`weekly limit`).

## Что не является причиной

- **DeepSeek**: провайдер и ключ не трогали, `api.deepseek.com` из схемы не убирали.
- **Telegram**: токен и `hermes-gateway` в коммите не менялись.
- **Переустановка Hermes** (06.08): после неё агент штатно работал две недели.

## Итог

Агент лёг не «сам по себе» и не от подписки как таковой. Его перевели на маршрут,
который: (а) содержит дефект, отдающий пустой ответ вместо ошибки, и (б) на каждое
сообщение поднимает полноценную агентную сессию Claude Code с opus и обходом vault.
Первое даёт тишину, второе — деградацию и риск OOM.

Возврат на DeepSeek снимает обе причины сразу, потому что этот маршрут идёт прямым
HTTP-запросом в `api.deepseek.com`, минуя локальный прокси и CLI.

## Порядок действий

```bash
# 1. Вернуть рабочий маршрут (около минуты)
bash kleo-rollback-deepseek.sh

# 2. Собрать доказательства финальной причины
bash kleo-diagnose.sh
```

Скрипт отката делает бэкап `config.yaml`, правит только три ключа, снимает
зависшие процессы `claude -p` и перезапускает gateway. Живой конфиг копией из
restore-kit **не** перезаписывается — там часть значений затёрта на `REDACTED`.

Прежде чем возвращаться на подписку Claude Code, накатите
`claude-code-openai-proxy.fixed.py` — иначе дефект с пустым ответом вернётся вместе
с маршрутом.
